# View 扩展架构

本文记录 Memsphere View 的长期扩展架构基线。它描述稳定的产品边界和系统职责，不规定当前版本必须一次性实现的全部细节。

## 背景

Memsphere 是个性化软件的运行环境。一个 Project 可以包含多个相互独立的软件单元：一份程序化 Memory 可以是一个软件，一个独立的 View 模块也可以是一个软件。软件不再要求以传统应用的形式整体打包。

View 是人操作这些软件的入口。它既要承载 Memsphere 官方功能，也要允许用户在安装 Memsphere 之后编写自己的界面，并把这些界面组装进同一个产品外壳。

因此，用户代码不能进入 Memsphere 源码，也不能要求重新编译已经发布的 Memsphere。

## 架构目标

- Memsphere 发布后，用户仍可独立开发、安装和组合 View 模块。
- 官方界面与用户界面采用同一套扩展机制。
- 一个模块既可以贡献完整页面，也可以扩展其他模块明确开放的局部界面。
- 原型与正式模块使用相同结构，可以从可交互原型直接演进为正式功能。
- View 服务不持有业务状态，可以随时重启并从 Project 配置重新构建。
- 单个用户模块损坏时，基础 Shell 和其他模块仍然可用。
- Project 及其个性化软件资产可以迁移、复现和持续演进。

## 非目标

本文暂不设计：

- Data 的存储模型和访问协议；
- View Manifest 的具体字段；
- View SDK 的具体 TypeScript API；
- 非可信第三方代码的沙箱与权限模型；
- 不重启服务的插件热替换；
- 常驻的用户后台服务。

## 核心概念

### View Host

View Host 是 Memsphere 提供的最小浏览器运行基座，负责：

- 启动页面和稳定 Shell；
- 解析当前 Project 的 View 组合；
- 加载独立编译的模块 Bundle；
- 维护 Slot 注册表并组装界面；
- 提供稳定的 View SDK；
- 隔离模块启动和渲染故障；
- 在服务重启后协助浏览器恢复。

View Host 不承载 Memory、Run 等具体产品功能。这些功能由官方 View 模块提供。

### View 模块

View 模块是一份可独立开发、编译、安装和分享的界面能力。标准交付物至少包含：

- 模块描述文件；
- 编译后的浏览器 Bundle；
- 模块使用的静态资源。

模块可以贡献页面、导航项、工具栏操作、卡片、预览器或其他模块公开 Slot 中的内容。模块不能直接修改 View Host 或其他模块的内部 DOM，也不应依赖 Memsphere 的内部源码。

### View 模块实例

模块是代码，实例是 Project 对这份代码的一次具体使用。

同一个模块 Bundle 在 View Host 中只加载一次，但一个 Project 可以声明多个模块实例。例如，同一个表格模块可以同时产生“客户列表”和“任务列表”两个界面实例。每个实例拥有稳定 ID 和独立配置。

### Slot

Slot 是模块明确开放的 UI 扩展位置，也是 View Host 与模块之间、模块与模块之间的界面契约。

```text
View Host
└── Root Slot
    ├── Navigation Slot
    ├── Page Slot
    ├── Toolbar Slot
    └── 模块声明的子 Slot
```

Slot 的所有者负责定义位置、输入和组合规则，其他模块只能通过公开契约注册内容。模块可以在自己拥有的界面中继续声明子 Slot，由此形成一棵可扩展的界面树。

长期 Slot 模型需要支持单一内容、列表内容、按键选择和按条件选择等组合方式；具体类型及 API 在 View SDK 设计中确定。

## 总体结构

```text
Memsphere View Host
├── Boot Page
├── Stable Shell
├── Project Composition Resolver
├── Bundle Loader
├── Slot Registry / Renderer
├── View SDK
└── Failure Boundary

Project
├── 官方 View 模块实例
├── Project 内本地 View 模块实例
└── 已安装公共 View 模块实例
```

基础 Shell、Project 切换和故障页面属于 View Host，不允许模块替换。Memory、Run 等具体官方功能属于普通 View 模块，用户可以禁用或替换。

## 编译与加载

Memsphere 与用户 View 模块始终分别编译：

```text
Memsphere 发布
  → View Host + View SDK

用户开发 View 模块
  → 独立编译为浏览器 Bundle
  → Project 声明模块实例
  → View Host 启动时动态加载
  → 模块向 Slot 注册界面
```

生产环境不会把用户源码与 Memsphere 联合编译。开发工具可以监听用户源码并自动编译，但它只构建对应模块。

扩展协议不绑定 React、Vue 或其他 UI 框架。View Host 提供框架无关的挂载、数据和回调契约；官方工具链可以优先提供 React + TypeScript 开发体验。模块默认自行携带所需的 UI 框架，只依赖稳定的 View SDK。

## 安装与 Project 组装

安装和启用是两个概念：

- 公共模块可以安装到用户级模块仓库，被多个 Project 复用；
- Project 记录启用的模块、实例和精确版本；
- Project 内开发的本地模块随 Project 保存和迁移；
- 公共模块不必复制进每个 Project，但 Project 必须锁定版本并能报告缺失依赖；
- 公共模块升级由用户明确触发，不自动改变既有 Project。

原型模块从创建之初就使用正式模块结构。原型完成后可以原地完善、锁定版本或独立发布，不需要迁移到另一套工程。

## 运行与重启模型

Memsphere View 不采用 DSH 那种为热更新设计的复杂插件生命周期。它使用可重建的整体启动模型：

```text
启动 View
  → 读取当前 Project 组合
  → 解析模块和版本
  → 加载每个模块 Bundle 一次
  → 创建模块实例并注册 Slot 内容
  → 渲染界面

模块更新
  → 重新编译模块
  → 重启 View 服务
  → 浏览器自动刷新
  → 按相同组合重新构建
```

切换 Project 时允许整页重新加载，并根据目标 Project 重新组装模块，不要求在原页面中动态卸载和替换整棵插件树。

模块组件仍需支持普通的挂载和卸载，用于页面切换、释放 DOM 事件和测试。这是 UI 组件生命周期，不是插件热替换生命周期。

开发模式可以把“编译模块、重启 View、刷新浏览器”自动串联起来，但底层语义仍是完整重启。

## 无状态边界

View Host 是可丢弃的展示与交互运行时，不保存持久业务状态。服务重启后，界面必须能够根据 Project 组合和 View 外部的权威状态重新构建。

- 当前模块和页面位置保存在 URL 中；
- 浏览器检测到 View 服务重启后自动刷新并恢复 URL；
- 临时展开状态、悬浮状态等只属于浏览器；
- 未提交的表单草稿允许在刷新时丢失；
- 需要持久化的数据必须通过后续定义的正式数据契约写入 View 之外。

这一边界保证 View 可以随时重启、升级或替换，而不会中断 Agent 中的核心运行任务。

## 故障处理

用户会频繁创建和修改原型模块，因此一个模块失败不能导致整个 View 不可用。

- Bundle 缺失、版本不兼容或模块启动失败时，只禁用对应模块；
- Slot 注册冲突应明确指出模块、实例和 Slot；
- 模块渲染异常由故障边界捕获；
- Stable Shell、故障诊断页和其他健康模块继续工作；
- 依赖故障模块的模块可以一并禁用，但不得形成静默的半启动状态。

开发模式自动重启后仍保留清晰诊断，避免刷新循环掩盖真实错误。

## 信任与样式

当前阶段只加载用户自己编写或明确安装的可信代码，不为陌生第三方模块提供安全沙箱。可信不代表可以依赖内部实现：模块仍必须遵守 View SDK、Slot 和版本契约。

Memsphere 提供主题变量和标准界面能力，帮助模块融入官方 Shell，但不强制模块采用统一视觉风格。模块样式不得污染 Host 或其他模块；具体样式隔离机制在 View SDK 和前端实现设计中确定。

## 与 DSH 的关系

本架构参考 DeepSeek Harness 的微内核和客户端组合思想。

采用的原则：

- 产品功能通过插件式模块组合，而不是修改特权核心；
- 浏览器模块独立编译，由 Host 发现和加载；
- UI 通过类型化 Slot 形成组合树；
- Slot 只能由所有者声明，其他模块通过公开契约贡献内容；
- 官方模块与扩展模块使用同一机制；
- 模块代码与模块实例分离，同一份代码可以承担多个配置角色。

刻意不采用的部分：

- 为长时间运行 Session 服务的插件热更新；
- 每一项注册都必须可逆的 effect 系统；
- 配置变化触发的动态插件树卸载和重挂载；
- 为卸载、依赖丢失和热替换设计的精细停稳协议。

DSH 不能轻易重启，是因为重启可能中断大量正在运行的 Session。Memsphere 的核心运行发生在 Agent 中，View 只是可重建的辅助入口，因此整体重启是更适合 Memsphere 的复杂度选择。

## 后续设计

在本架构基线上，后续文档应依次明确：

1. View Manifest：模块身份、版本、Bundle、静态资源、SDK 兼容范围和依赖声明；
2. View SDK：Slot 声明与注册、模块实例上下文、路由、主题、挂载和故障协议；
3. Project Composition：本地模块、公共模块、实例配置和版本锁文件；
4. 开发工具链：创建模块、Mock 数据、监听编译、重启与浏览器刷新；
5. Data 契约：View 和 CLI 如何操作同一份用户数据；
6. 第三方分发：签名、权限、沙箱、市场和兼容性策略。

在这些细节确定前，实现不得让用户模块依赖 Memsphere 私有源码，也不得把联合编译作为扩展前提。
