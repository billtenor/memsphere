# Run 附属数据接入数据层与归档搬运

## 需求

将 Run 附属数据的持久化统一接入 DataStore，范围包括 Artifact、Memory 快照和 Agent 活动记录，使当前与归档数据的存储可以分别替换实现。Run 状态暂不接入，后续再进行领域模型设计，逐步完成整个 Run 的建模。Human（billtenor）和产品 Agent 共同担任产品负责人。

本轮将文件产物接入统一存储抽象。已有正式产物的文件位置、内容和现有配置保持不变；中间产物取消单独的 drafts 目录，统一按 Artifact 管理；Agent 通过另存为取得本地编辑副本，再统一上报 Artifact。归档与恢复须支持失败后 redo。本地契约已根据后续讨论修订，尚未替换第一轮评审中的不可变 Submission，需在评审流程允许修订后重新提交。

### 当前迭代范围

- 接入文件产物，包括正式 Artifact、逐步上报合成的中间 Artifact（旧实现称 Schema 草稿）、Review Submission 和上下文中的产物文件；Run 中内嵌的简单值产物保持不变。
- 将 Run 的 `memory/` 快照文件和 `agent-activity/` 活动记录一并接入 DataStore；活动记录同时包含 JSON 快照和 ACP JSONL 日志。
- 本轮不再仅改造 Artifact 存储，而是统一改造上述 Run 附属数据的持久化及归档、恢复访问链路。Run 状态文件仍使用现有持久化方式，不在本轮完成其领域模型设计。
- 文件产物的写入、读取、归档与恢复接入 DataStore，覆盖 CLI、View、Review 及内部产物读取链路。
- Artifact 列表、归属和元信息继续由原有 Run 与 Review 记录管理；DataStore 只负责按 DataId 访问内容，不使用 `Store.list()` 发现或筛选 Artifact。
- 已有正式产物原地使用，正式产物仍使用原有存储位置和内容格式。中间产物是已确认的布局变更例外：不再单设 drafts 目录，使用正式 Artifact 所在的存储布局，由 Run 状态记录其中间状态。归档与恢复仍落到原有对应位置。
- 提供统一的 Artifact 另存为能力，支持正式和中间文件产物导出到 Agent 指定位置；上报统一使用 Artifact 上报流程，不新增草稿专用保存或提交命令。
- 配置能力、字段、默认值与含义和过去保持一致，不新增面向用户的 Store Factory/Config 配置入口，不要求用户改配置。

### 后续范围

OSS 等其他存储后端、存储配置能力的扩展、Run 状态的领域建模，以及内嵌简单值产物接入均不在本轮范围。未来如有需求另行讨论；本轮不建设数据迁移工具或新旧格式兼容机制。

### 已确认的设计

- 保持 `Data = id + model + payload`；Artifact 使用同一个采用 raw 标准的模型。
- Model 与 Store 为一对多关系；每个 DataStore 或 ValueStore 只绑定一个模型，不混存多个模型的数据。
- StoreId 由业务在装配或创建 Store 时显式指定，不由框架生成；在当前 Project 内唯一，不直接决定物理存储位置。
- Store 保留 `id` 和 `model`；Factory 接收 StoreId；StoreRegistry 和 DataManager 按 StoreId 登记、查找或准备 Store；StoreBinding 增加 id。
- 当前 Artifact Store 和归档 Artifact Store 是两个独立实例，均采用 filesystem；内部装配沿用现有位置与配置，后续可以分别替换实现。
- 每个 Project 使用当前和归档两个 Artifact Store，不为每个 Run 单独创建 Store；不要求 filesystem Store 理解 Run 的业务目录规则。共享物理目录中的其他文件不因接入而被当成 Artifact 管理。
- 扩大范围不改变“每个 Store 只绑定一个模型”的约束，也不意味着将所有 Run 文件混存为 Artifact。Memory 快照、Agent 活动记录采用哪些模型及 Store，尚待讨论；此前提出的三类模型、每类两个 Store 只是建议，并非已确认方案。
- 多副本、迁移和跨 Store 一致性由业务实现，不新增抽象层的多副本写入或跨 Store 事务协议。
- PayloadContent 只保证一次消费，不保证重复调用 `stream()` 能重放内容。再次读取已保存的数据时重新 `get()`；内容可由生产方持续提供，以正常 EOF 表示结束。
- DataStore 的 `create/update` 继续接收完整 Data，消费其中的输入流，返回 `Promise<void>`：正常 EOF 且保存完成后成功，流错误、取消或存储失败时拒绝，不回传 StoredData，不引入 DataWrite 或双向 Payload 接口。
- 追加是可选能力，以 `AppendableDataStore.append(context, data): Promise<void>` 表达。只追加到已有记录，模型和 contentType 必须一致；不自动创建，不插入换行，不合并 JSON。失败或取消可能留下已写前缀，不能直接重试整个输入。
- filesystem DataStore 逐块写入：create/update 在输入完成后发布完整文件；append 渐进写入已有文件。保留现有无文件锁的实现，不承诺整条追加流在并发写入时连续或原子完成。
- ValueStore 本轮只同步 StoreId，`create/update` 仍返回 StoredValue。
- 受管理的中间 Artifact 纳入 DataStore；另存为导出的本地编辑副本，以及 Agent 自行创建的临时文件，不纳入 DataStore。本轮不将 Run 状态改造成 ValueStore。

### 中间产物与 Agent 操作

- Agent 面向统一的 Artifact 操作，不需要单独操作一种名为草稿的资源；“草稿”只是框架内部对合成中间状态的称呼。
- 逐步上报时，框架合成并持久化中间 Artifact，在 Run 状态中记录关联和阶段；文件所在目录不表达阶段。
- Agent 可以将正式或中间 Artifact 另存为到指定的本地文件并编辑。导出和本地编辑本身不修改受管理内容，也不推进 Run。
- Agent 编辑后统一上报 Artifact。上报读取提交文件的内容，按当前步骤校验，通过后进入原有接纳或评审流程；不增加“先写回草稿、再正式提交”的两次操作。
- 不再要求最终上报文件必须是框架内部存储的原始路径；本地编辑副本不作为后续读取 Artifact 的持久化依赖。
- 存储位于本地还是未来的云端，不改变上述交互方式。本轮不实现云端后端。
- Review Submission 及其上下文继续保持不可变，不能被后续中间产物更新或重新上报覆盖。

### 归档、恢复与 redo

- Artifact 根据原有业务记录提供的清单，在源、目标 DataStore 之间搬运；即使两端都是本地 filesystem，也不以目录 rename 代替 Artifact 的跨 Store 搬运。恢复采用反向流程。
- 已确认顺序：复制全部相关 Artifact，确认目标内容完整正确，再切换归档或恢复的有效位置，最后清理源 Store 中该 Run 对应的 Artifact；不删除整个 Store。
- 复制或校验失败时，不切换有效位置，不提前删除源 Artifact；切换后的源清理失败允许保留副本，但必须明确提示尚未清理完成并支持 redo。
- redo 指同一次归档或恢复在失败、中断后可以重新执行并完成，不要求用户手工修补文件。已完成的工作不能导致重试破坏数据；目标已有内容不能未经核实就覆盖或当作成功，不得误删其他 Run 的数据。
- Memory 快照与 Agent 活动记录也纳入跨 Store 搬运和 redo 的范围，具体清单来源与搬运协调方式待实施方案讨论。
- Run 状态等未纳入本轮 DataStore 的文件，继续沿用文件系统归档与恢复方式；中间 Artifact、Memory 快照和 Agent 活动记录不再归入这类其他文件。协调时，不得让原有目录移动再次搬运、覆盖或误删由 DataStore 管理的内容。
- 不新增归档日志、进度文件或其他中间状态存储，包括不为记录搬运进度向现有 Run 记录追加检查点。redo 依据现有业务记录和两端实际内容判断。此约束不禁止前述用于表达中间 Artifact 阶段的 Run 业务状态。
- redo 的具体进度识别、冲突处理、校验方法、状态切换及其他文件移动的协调方式仍须以实际代码验证；若不增加中间状态就无法安全判断，不猜测成功或删除数据，先报告具体场景并与 Human 讨论。

## 交付要求

### 接口实现先行，等待 Human review

Human 要求先完成已确认的接口调整及对应实现、测试和文档，单独进行代码 review；确认没有问题后，再继续此前的需求交付流程。这个检查点不代表 Run 存储迁移已经实施或正式需求评审已通过。

本检查点仅包含 StoreId、一模型多 Store、Payload 单次消费、DataStore 流式输入与写入返回值、可选 append 及配套实现。暂不接入 Run、不改 Artifact 命令、不实施归档恢复，不替代第一轮不可变评审 Submission，也不自动推进原 Run。

### 技术方案决策须先与 Human 讨论

本次确认门禁不限于 `src/data/api`。遇到需要选择或调整技术方案的问题，必须先与 Human 讨论并取得明确结论，再实施，不能仅以“属于实现层”为由自行决策。

- 门禁包括公共抽象、持久化结构与位置、配置、兼容或迁移策略、归档与恢复机制、失败恢复与一致性方案，以及其他需要作出技术方案选择的问题。
- 后续如需新增、删除或调整该层的接口、类型、字段、方法签名或既有契约语义，Agent 必须先向 Human 说明问题、可选方案、影响与风险及建议，讨论并取得明确结论后，才能实施相关变更。
- 即使不修改接口文件，也不得通过实现改变该层已确认的公共语义而绕过讨论。
- 上述已确认的数据层接口方案无需重复审批；新增决策或偏离已确认方案时须重新讨论。
- Agent Reviewer 的意见或通过票不能替代 Human 对技术方案的明确确认；不得先实现后补确认。
- 未决时暂停依赖该决策的实现，可以继续调查、提出方案或完成不依赖该决策的工作。
- 已确认方案内、不涉及新方案选择且不改变契约或用户行为的编码、测试和整理可以自主推进；不得借此改变需求范围或降低验收标准。无法判断是否属于新决策时，先询问 Human。
- 实施方案和交付报告须列出本轮技术决策、对应的 Human 确认结论及实际落地情况，保证可追溯。

## 向前兼容

结论：需要向前兼容，范围包括已完成的正式 Artifact、Memory 快照、Agent 活动记录、已有归档及现有配置；保留其文件布局、内容和既有读取、展示、归档、恢复能力，直接沿用已有文件，不建设新旧格式兼容分支。若活动日志接入方案需要改变这一边界，必须先与 Human 决策。

中间产物例外：结论为不需要向前兼容旧 drafts 设计。取消单独目录，并调整中间产物的 Run 状态表示和操作方式；不承诺升级前停在旧草稿阶段的 Run 能继续原填写流程，不建设旧草稿迁移或恢复机制。此例外不扩大到已有正式产物及归档，也不授权批量删除旧 drafts 文件。

当前本地可见 Tag 中没有名称含 `stable` 的稳定 checkpoint，不声称已核实远端 Tag，也不扩展到任意历史版本。本轮以变更前的正式产物文件结构与行为为回归基线；上述兼容范围内的记录无需迁移或修改配置即可继续使用。中间产物与 Agent 编辑交互按本轮已确认的新要求验收。

## 验收标准

- 同一个 Artifact 模型可绑定两个不同 StoreId，两个 Store 的配置和数据互不混淆；每个 Store 仍只接受绑定模型的数据。
- 存储身份与物理后端分离，Data 本体不增加 StoreId。
- 正式产物保持原有存储布局和内容格式；中间产物按本轮新要求使用同一布局，不再创建 drafts 专用目录，由 Run 业务状态区分阶段。不添加存储信封、特殊编码或旧草稿迁移要求。
- 已有当前和归档文件可原地读取，CLI、View、Review 及内部产物读取结果保持一致，Review 产物摘要不变。
- Memory 快照通过 DataStore 保存和读取后，原有内容、目录结构及 Run 使用快照的行为不变。
- Agent 活动 JSON 快照与 ACP JSONL 日志通过 DataStore 持久化后，活动记录、读取、展示及日志重建行为保持正确；覆盖持续写入与相关失败边界，具体验证方案待追加写入方案确定。
- Memory 快照和 Agent 活动记录随 Run 一同归档、恢复，纳入搬运完整性和 redo 验证，不遗漏为继续直接读写原位置的旁路。
- 归档、恢复保持原有目标位置和正常操作结果；Artifact 通过两个 Store 搬运，其他文件沿用原有文件系统方式。不丢失产物，不误删其他 Run 的内容，不将不完整操作报告为成功。
- 验证复制中途、目标校验、有效位置切换及源清理阶段失败或中断后的 redo；重试最终收敛到正确结果，无需用户手工修补。覆盖目标已有内容和重复执行场景，不能静默覆盖冲突内容。
- redo 不依赖新增中间状态存储；正常中断后的重试和数据本身冲突或损坏须区分，后者明确报错并保留数据，不虚报成功。
- Artifact 列表和搬运清单来自原有业务记录，不依赖 `Store.list()`；目录中其他文件不被当作 Artifact 枚举、搬运或删除。
- 正式和中间文件产物均可另存为到指定本地位置，字节内容保持一致；本地编辑不会自动改变受管理 Artifact。统一上报接受合法的本地副本，通过后进入正常接纳或评审流程；失败不得推进步骤或改变已冻结评审内容。
- 旧 drafts 的未完成流程不属于兼容验收范围，但其中间状态记录不能阻止读取同一 Run 中已经完成的正式产物。
- 现有配置无需修改，无新增必填配置或设置入口；简单值产物的持久化不变，Run 状态仍按现有文件系统方式持久化，中间 Artifact 业务状态允许按本轮要求调整。
- 保持 Linux、Windows、macOS 支持，并覆盖路径处理及相关失败边界。
- 技术方案决策均符合上述 Human 确认门禁；交付材料能追溯确认结论与实际变更。
