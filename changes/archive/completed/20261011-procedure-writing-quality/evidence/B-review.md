# 修复候选流程独立 review

结论：建议修改后再验收。流程主干已覆盖取证、高风险 Human 补充、批准后演练、失败后改进并重新批准、调用验证后判断重试和最终交付；但局部规则全局化、字段职责混写、修订契约丢失及批准/验证衔接问题会影响可靠执行。以下只提出修改方向，不修改或执行被评审流程。

## 范围与依据

- 当前隔离 Project：`writing-evaluation`。通过 Memsphere Procedure 列表选择 `procedures/memsphere-general-task-execution` 作为审查任务入口；未启动 `repair-release-candidate` 或 `repair-validation`。
- 全文审查 `memories/procedures/release-candidate.yaml`（逻辑引用 `procedures/repair-release-candidate`），包括所有条件、分支、循环、内联 Artifact/Schema。
- 全文追溯其引用：`memories/procedures/repair-validation.yaml`、`memories/statements/repair-evidence-rules.yaml`。已确认三份文件与当前 Project Memsphere 读取来源逐字节一致。
- 完整读取并应用 `statements/memsphere-procedure-writing-rules`，结合 Procedure、Statement、Schema、Memory 概念及 Procedure/Schema 规范；按语法规则核对缺省类型、Schema 字段及控制节点语义。业务验收依据为 Human 本次提供的背景。
- 下列行号均指上述 `memories/` 文件，而不是 CLI 展开后的文本。严重度：“高”影响业务执行或判定；“中”影响契约、作用域或规范符合性。

## 可行动问题

### 1. 高风险缓解意见被要求出现在每一步（高）

**定位：** `release-candidate.yaml:8`，Procedure.asserts“每个步骤都必须提供高风险缓解意见”；对照第 23–35 行高风险 If 和 Human Action。

**原因：** 该全局规则同时约束低风险路径、取证、boolean 条件和验证子流程。它既超出“风险高时由 Human 补充”的业务范围，也要求 boolean 产物承担意见文本，且让 Agent 步骤承担 Human 的职责。

**修正方向：** 取消这条全局化表达，将提供缓解意见的要求限于高风险分支的 Human Action，保留该分支及 `actor: human`。后续方案应将这份意见作为适用输入，见问题 10；不能为了精简删除缓解要求。

### 2. 所有步骤列证据引用，扩大了共享 Statement 的作用域（高）

**定位：** `release-candidate.yaml:10`；第 40–41、116–117 行的 Statement 引用；`repair-evidence-rules.yaml:4–6`。

**原因：** 全局“所有步骤都必须列出证据引用”扩展到 Human 意见、条件 boolean 和整个验证调用链，并与方案、报告已经引用的证据规则形成语义重叠。Statement 的业务范围是方案和最终报告，规则不应因被复用而成为全局要求。

**修正方向：** 删除过宽的全局表达，保留方案和报告 Action 的 `asserts: !ref`，在修订方案的适用步骤继续引用（见问题 8）。取证 Schema 的“证据引用”和子流程自己的“证据”字段继续保留。单工单边界第 6 行属于合理全局规则，必须保留。

### 3. 风险字段要求跨作用域，方案 action 混入强制规范和建议（中）

**定位：** `release-candidate.yaml:9`、第 37 行 action、第 50 行 Schema 的“风险解释”。

**原因：** “每项风险必须关联证据”是风险解释字段的内容约束，却放在 Procedure.asserts；“必须标明未确认假设”是强制语义，“建议按影响程度排序”是非强制建议，却都写进 action。三者均不是要做什么的动作描述。

**修正方向：** action 保留准备修复方案的动作和必要输入；将“风险解释”由字符串简写改为具名 `!schema`，在该字段 `asserts` 中保留每项风险与证据关联、未确认假设标识，在字段 `suggests` 中保留按影响程度排序的建议。去掉其全局/动作中的重复表达，修订版本也适用同一字段契约。不得弱化两项强制语义。

### 4. 遗留问题为空的说明要求误放全局（中）

**定位：** `release-candidate.yaml:7`；第 126 行“遗留问题”字段。

**原因：** 这条规范只约束最终报告的遗留问题内容，不是整个调用链持续生效的业务边界。全局放置使无关步骤接收最终报告的局部要求。

**修正方向：** 将“遗留问题”展开为具名 Schema 字段，把“为空时必须说明依据”放在字段 `asserts`；保留其必填性以及说明依据的要求，不能直接删除。

### 5. 取证步骤重复声明机器契约（中）

**定位：** `release-candidate.yaml:13–22`。

**原因：** action 的“使用 YAML 输出工单、影响对象和证据引用字段”、第 15 行“必须使用 YAML”，与 Artifact 的 `type: object`、`format: yaml`、Schema.fields 已表达的内容重复，且格式/字段清单越界进入 action。

**修正方向：** action 保留“收集并整理指定工单证据”及所需输入；YAML、对象结构和三项必填字段由现有 Artifact/Schema 负责，删除重复的自然语言格式要求。保留取证动作、格式和字段，不将字段改为可选。

### 6. 初始方案重复结构和格式，格式被再次包装为建议（中）

**定位：** `release-candidate.yaml:39`、第 43 行及第 45–50 行。

**原因：** 三个必填字段已由 Schema.fields 声明，再在 asserts 列出是重复；Markdown 已由 Artifact.format 强制声明，“建议采用 Markdown”复述机器契约并模糊其强制程度。

**修正方向：** 保留对象、Markdown outline 和三个字段的机器契约，删除重复的字段清单 asserts 和格式 suggests；保留证据 Statement 引用及问题 3 的风险内容规范。不得把 Markdown 契约降成可选建议。

### 7. 最终报告混合条目部分重复，结论内容规范未放到字段（中）

**定位：** `release-candidate.yaml:115`，对照第 126 行“结论”字段；第 118–119 行简短句子建议。

**原因：** “报告必须包含结论”由 Schema.fields 已经保证；“结论必须解释修复对账结果”则是机器结构没有表达的必要语义，不能随重复部分一并删掉。该语义只约束结论字段。简短表达是非强制建议。

**修正方向：** 删除“必须包含结论”的重复部分；把“结论”展开为具名 Schema 字段，在字段 asserts 保留解释对账结果，在字段 suggests 保留简短句子建议。继续保留报告 Action 的证据规则引用。Human 所说“摘要简短只是建议”不能被改写为强制字数门槛，也不意味着必须新增摘要字段。

### 8. 方案修订和失败改进丢失初稿契约（高）

**定位：** `release-candidate.yaml:65–69`（已修订方案）、第 94–98 行（原因与改进方案）、第 107–111 行（调整后的改进方案）；对照第 36–50 行初始方案。

**原因：** 初稿是带结构的 object Markdown outline，后续产物只声明 `format: markdown`，缺省 `type: string`，未引用证据规则、未包含风险字段的内容规范。原 Action 的 asserts 不自动传给另一个 Action。Human 因而可以批准一份缺少修复动作、风险解释、验证计划或证据支撑的修订文本。

**修正方向：** 三处都明确产出当前完整方案，并沿用初稿的对象类型、outline、字段结构、字段内容约束及证据 Statement 引用；可复用同一 Schema，或在适用 Action 中分别声明/引用。失败原因仍需保留，可以与完整改进方案分字段表达。若选择只产出差异，则必须另有明确的合成和完整方案检查步骤，之后才请求 Human 批准，不能让差异文本直接替代完整方案。

### 9. 改进方案未获批准时，没有明确收集 Human 修改意见（高）

**定位：** `release-candidate.yaml:99–111`，尤其第 101 行 Human boolean condition 和第 108 行“根据 Human 意见调整改进方案”。

**原因：** 该 condition 只产出是否待批准的 boolean，并不产出修改意见。do 中直接要求 Agent 根据意见调整，却没有安排 Human 提供这些意见；不能从 true 推导修改内容。初始批准循环第 59–64 行已经有正确的 Human 意见步骤，但它不覆盖改进循环。

**修正方向：** 在改进循环 do 中先显式安排 Human 提供改进方案修改意见，再让 Agent 根据该产物修订，随后重新执行 Human 批准 condition。继续保留“Human 明确批准后才能下一次演练”，不得让 Agent 代为批准。

### 10. 方案准备与演练的必要输入及最新方案选择不够明确（高）

**定位：** `release-candidate.yaml:25`、第 37 行、第 53 行、第 80 行，以及第 95、101、108 行。

**原因：** 高风险判断未指明依据前序工单证据；准备方案未指明使用工单证据及高风险分支的 Human 缓解意见。失败后可能留下初稿、初次修订、改进和再次调整的多个方案，但演练仍只说“按已批准方案”，没有明确选择当前工单最新一版被 Human 批准的完整方案。输入关系依赖执行者自行猜测，可能出现意见被遗漏或重试使用旧方案。

**修正方向：** 在相应 action 的必要输入中明确前序证据、适用的缓解意见、当前版本方案；改进或调整后更新当前方案，Human 判断针对该完整版本，演练使用最近明确批准的当前版本。修复动作/验证计划还应说明如何落实适用的缓解意见；未采纳时说明理由供 Human 判断。共享产物名称与必要输入引用不属于语义重复，不应为了去重删掉。无需虚构本次背景没有给出的风险分级阈值。

### 11. 验证结果的“是否通过”实际是 string 契约（高）

**定位：** `repair-validation.yaml:16`，Schema.fields 中的字符串简写“是否通过”；对应 `release-candidate.yaml:74`、第 89 行的后续判断。

**原因：** 字符串简写字段按规范推断为 string，不会因字段名叫“是否通过”而推断为 boolean。自然的 YAML `是否通过: true` 与当前字段类型不符；若改用文本，后续判断又需自行解释“通过/未通过”等值。

**修正方向：** 将该字段展开为具名 `!schema` 并显式声明 `type: boolean`，使子流程返回值和后续控制判断有一致的契约。保留第 9 行“全部影响对象完成对账且不存在未解释偏差才能通过”的强制语义；外层 Artifact 继续是 object，不将普通验证 Action 改成控制用 boolean Artifact。

### 12. 失败分支和重试条件未共同指向本轮验证结果（中）

**定位：** `release-candidate.yaml:70–92`，特别是第 74 行“根据验证子流程结果”和第 89 行“判断验证是否未通过”；引用 `repair-validation.yaml:7–16`。

**原因：** 已有“首次 true、验证通过才 false”的规则应保留，但多轮 Call 会留下多份同名“验证结果”。失败 If 未明确以刚结束的本轮验证结果为依据，下一次 While 也未指明最近一轮结果；缺失/不完整结果如何处理尚不明确。可能错误选择历史通过结果，跳过改进或提前退出。

**修正方向：** 明确两处条件都使用当前工单、本轮演练对应的最近已完成 Call 的“是否通过”字段：本轮 false 进入改进及重新批准，随后重试；本轮 true 跳过改进并在下一次 While 判断退出。首次仍返回 true，结果缺失或无效不能视作通过。保留 `!call target: repair-validation`，不把 Call 当作 boolean，也不新增 DSL 不支持的 Call 返回/绑定字段。

## 必须保留的正确内容

- 第 6 行单工单边界是贯穿全部分支、循环和子流程的合理全局约束。
- 高风险 Human 分支、初始 Human 修改意见/批准循环、失败后的改进/重新批准循环及验证 Call 都有业务必要性；修正上述问题不应删掉这些步骤。
- 方案和报告各自引用 `repair-evidence-rules` 的位置合理；该 Statement 本身没有发现需要修改的独立问题。风险逐项关联证据比一般证据引用更具体，不能作为重复要求删除。
- “解释修复对账结果”“空遗留问题说明依据”“未确认假设标识”是内容约束，不能仅靠存在字段替代。
- 首次演练与通过才退出、验证覆盖全部影响对象且无未解释偏差、报告 `final: true` 应保留。按影响程度排序及简短表达继续作为建议。
