## 可行动问题

### 1. 高风险缓解意见被错误要求于每个步骤

位置：根 `asserts` 第三项，第 8 行；高风险 `!if.then`，第 23–35 行。

原因：业务要求是在高风险分支由 Human 补充缓解意见；全局“每个步骤都必须提供”会同时约束证据收集、低风险分支、批准判断和 boolean 条件，甚至在尚未判断风险前就要求缓解意见。它扩大了义务且与条件产物不兼容。

修正方向：将该要求收敛到高风险分支的 Human Action。保留 `actor: human`、风险判断和缓解意见产物；已有 action 已表达提供意见，无需再逐字重复。准备方案时明确使用已收集证据及高风险分支实际提供的缓解意见作为必要输入，使该分支结果进入方案决策。

### 2. 所有步骤列证据引用的全局要求扩大了业务作用域

位置：根 `asserts` 第五项，第 10 行；方案和最终报告的 Statement 引用，第 40–41、125–126 行。

原因：`repair-evidence-rules` 定义的是方案和最终报告共享的引用规范；目前两处局部引用正确。全局条目又把“列出证据引用”强加给 Human 意见、所有条件和其他步骤，其中 boolean 产物无法承载引用清单。在方案、报告上也与局部引用语义重叠。

修正方向：取消这条泛化的全局义务，保留方案、最终报告的局部 Statement 引用和证据收集 Schema。不要删除“引用当前工单证据以支撑业务判断”的语义要求；字段存在只保证结构，不能保证判断得到证据支持。对账步骤已有自身的证据字段和验证职责，按该步骤范围处理。

### 3. 风险字段专属约束放在流程全局

位置：根 `asserts` 第四项，第 9 行；修复方案 Schema 的“风险解释”，第 50 行。

原因：“每项风险必须关联证据”只约束风险解释内容，其他步骤并没有风险解释字段。它也不等同于 Statement 的产物级证据引用：列出一组证据不保证每项风险都有对应证据。

修正方向：把“风险解释”由字段简写改为具名 `!schema`，将每项风险与证据的关联要求放入该字段的 `asserts`。完整保留该约束，并让后续修订的方案继续适用。

### 4. 最终报告遗留问题的要求错误提升为全局

位置：根 `asserts` 第二项，第 7 行；最终报告 Schema 的“遗留问题”，第 135 行。

原因：“遗留问题为空时必须说明依据”是最终报告中特定字段的条件内容要求，无法持续适用于收集、风险判断、批准和演练。字段必填也没有表达“无遗留问题”的依据要求。

修正方向：将其下沉到最终报告“遗留问题”字段的 Schema.asserts，保留为空或声称无遗留问题时必须给出依据的语义，不应为精简而删除。

### 5. 证据收集动作重复了机器契约

位置：首个 Action 的 `action`，第 13 行；其 `asserts`，第 15 行；Artifact/Schema，第 18–22 行。

原因：动作中的“使用 YAML 输出工单、影响对象和证据引用字段”和断言“必须使用 YAML”已分别由 `format: yaml`、`fields` 表达，重复了格式和字段契约，且把产物结构混入动作。

修正方向：action 保留“收集并整理指定工单证据”的执行意图和对象；移除重复的格式断言及 action 中的格式、字段清单。保留 object、YAML 和全部三个字段，不删证据收集动作或必要输入。

### 6. 准备方案动作混入字段内容要求和非强制建议

位置：方案 `action`，第 37 行；风险解释字段，第 50 行。

原因：“风险解释必须标明未确认假设”是字段内容规范，“建议按影响程度排序”是书写建议，均不属于步骤动作。混写使强制与建议的职责不清，且不能在字段填写时按最小作用域提供要求。

修正方向：action 仅保留准备方案的动作、执行对象和必要输入。把标明未确认假设放到“风险解释”字段 Schema.asserts；按影响程度排序放入该字段 Schema.suggests，与问题 3 的证据关联一起保留。排序不得升级为强制要求。

### 7. 方案的必填字段和格式被重复声明

位置：方案 `asserts` 第 39 行、`suggests` 第 43 行；Artifact/Schema，第 46–50 行。

原因：“必须包含修复动作、风险解释和验证计划”重复必填字段；“建议采用 Markdown”重复已强制声明的 Markdown 契约，还将同一要求表述为建议。

修正方向：移除这两条重复文本，保留原有三字段、object、Markdown outline 和局部证据 Statement 引用。不要把证据支持判断、风险关联或假设说明当成字段存在即可满足的要求一起删除。

### 8. 方案修订后失去原方案的结构和语义契约

位置：初始方案第 36–50 行，对照“根据意见修订方案”及“已修订方案”，第 65–69 行；失败改进与调整产物，第 103–120 行。

原因：初始方案是有三个必填字段的 object/Markdown outline，且局部引用证据规范。批准循环中的已修订方案退化为默认 string/Markdown，未沿用 Schema 或证据要求；失败后的改进和调整同样缺少完整方案契约。允许仅提交一段修改说明，丢失风险解释、验证计划或证据支持后仍进入批准。初始 Action 的局部约束不会自动适用于另一个 Action。

修正方向：凡形成新的待批准执行方案，都应沿用完整方案契约，包括结构、证据引用、每项风险关联证据及假设说明。可以复用同一 Schema/Statement，或在这些 Action 的适用位置声明；不要通过扩大为流程全局来解决。失败原因说明可另保留，但须明确它如何产生完整的下一版方案，而不只是补丁建议。

### 9. 演练失败没有可靠进入修改和重新批准路径

位置：演练结果第 79–84 行；对账通过要求第 86–95 行；失败分支条件第 96–101 行；外层继续判断第 72–74 行。

原因：演练结果只有无 Schema 的 YAML object，没有明确成功/失败结果；失败分支只判断“验证是否未通过”。当前验证通过的显式约束只覆盖完成对账且没有未解释偏差。如果演练失败但未改变账目，对账仍可能满足上述条件，流程就可能绕过修改和重新批准，并因验证通过退出。

修正方向：在演练结果中明确记录本轮执行结果与失败依据；在通过判据或失败分支中明确演练失败也必须触发修改并由 Human 再批准。仍保留演练后的对账验证及全部影响对象、未解释偏差的约束。继续演练条件应严格依据最新一轮结果，只有演练和对账验证均满足成功标准才退出，不能用先前轮次结果代替本轮。

### 10. 改进批准循环引用了未收集的 Human 意见

位置：改进批准条件第 109–114 行；循环体“根据 Human 意见调整改进方案”，第 116–120 行。

原因：该 Human 条件仅产出 boolean。返回 true 表示尚未批准，但不会提供可供调整使用的意见；循环体没有像初始批准循环第 59–64 行那样安排 Human 提供修改意见的 Action。Agent 因此缺少必要输入，容易自行猜测 Human 意图。

修正方向：在改进未批准的 do 中，先由 `actor: human` 的 Action 收集本轮修改意见并记录为 Artifact，再据此调整完整方案，重新交由 Human 判断。保留批准条件由 Human 执行，不用 Agent 代判或将 boolean 假作意见。

### 11. 当前方案、批准版本与下一轮演练输入缺少明确关联

位置：初始批准条件“当前方案”，第 53 行；修订方案第 68 行；“按已批准方案完成演练”，第 80 行；改进批准条件及调整方案第 110、119 行。

原因：流程生成多个不同名称的方案产物，却未明确“当前方案”在修订后如何指向最新版，也未明确下一轮采用已批准的改进/调整方案替代上一轮方案。Memsphere 上报会保留独立产物，产物名称本身不表达版本替换。即使修改和批准都发生，仍可能重复演练旧方案，使改进路径失效。

修正方向：在相关 action 的必要输入中明确使用最近一次形成的完整待批方案；Human 必须批准该版本，下一轮演练必须使用该版本。保留批准与实际执行版本的可追溯关联，可采用方案标识或清晰的产物引用约定；不要声称自然语言会自动建立运行时变量绑定，也不必引入未经规范支持的 YAML 字段。

### 12. 验证通过字段没有表达预期的 boolean 值契约

位置：验证结果 Schema 第 95 行，“是否通过”是字符串字段简写。

原因：根据 Schema 缺省规则，字符串简写字段对应 string，并不会因为中文名称自动变成 boolean。下游两个条件需要稳定的通过/未通过判断，却可收到自由文本，与 boolean 控制判断之间还缺少明确对应关系。

修正方向：将“是否通过”声明为具名 Schema 字段并显式 `type: boolean`；在失败分支中明确根据本轮验证结果的该值判断，在外层继续条件中沿用同一轮结果及首次 true 规则。对账通过的业务判据继续保留在验证步骤适用范围内。条件仍须由各自 boolean Artifact 上报，不能假定字段自动控制分支。

### 13. 最终报告重复结论结构要求，字段语义与建议作用域过大

位置：最终报告 `asserts` 第 124 行，`suggests` 第 128 行；Schema 第 135 行。

原因：“报告必须包含结论”已由必填字段表达；“结论必须解释修复对账结果”是尚未被结构表达的结论字段专属规范，不能随去重删除。“结论优先使用简短句子”也是字段书写建议。业务请求说摘要简短只是建议，但目前没有摘要字段，现有建议实际约束结论，不能将两者等同。

修正方向：去掉重复的“必须包含结论”，把解释修复对账结果下沉到结论 Schema.asserts；将现有结论简短建议放到结论 Schema.suggests。若需要另行承载摘要简短建议，应明确它针对摘要内容，并保持非强制；不能据此强制新增必填摘要、限制报告解释内容，或删除必要证据和对账说明。最终报告的证据 Statement 引用保留。
