# 当前迭代需求契约：流程记忆撰写质量

## 整体目标

让后续 Agent 在新建或修改 Memsphere 流程记忆时，能够正确组织动作、产物、强制规范和建议，恰当地选择约束作用域，减少信息噪声，同时保留任务真正需要的要求。需求描述聚焦问题、理想态、范围与验收；具体实现方式在需求确认后的实施与验证方案中决定。

## 当前问题

1. action 被当成所有信息的容器，混入产物定义、格式要求、验收规范、建议和操作流水账，步骤动作不清晰。
2. Agent 对 action、artifact、asserts、suggests 四个字段的职责边界理解不稳定，容易将信息放错字段。
3. 同一要求在不同字段、Schema 或已经适用的规则中重复描述；典型情况是 artifact 已定义格式，asserts/suggests 再次要求该格式。不同措辞也可能表达同一要求。
4. Agent 混淆全局约束、步骤约束和字段约束，把仅适用于局部的要求随意提升为全局要求，造成全局规则堆积及作用范围扩大。
5. Agent 能解释上述概念，但实际写记忆时仍反复出现这些问题；仅有概念说明或语法校验通过，不能证明写作表现符合预期。

## 理想态

- 阅读 action 就能理解当前步骤要做什么；产物定义、格式和字段结构、验收规范、非强制建议不会混写成动作。
- artifact 能独立标识步骤产物及其机器契约；asserts 补充强制语义规范和必要执行约束；suggests 表达非强制建议。
- 同一要求只被完整声明一次。已由 artifact/schema 表达的类型、格式、布局和结构不再被自然语言重复；混合要求中独有的语义仍被保留。
- 约束的作用范围与实际适用范围一致。仅适用于某一步骤、产物或字段的规则不会成为全局规则；跨流程持续生效的必要规则不会被误删或错误缩小。
- 后续 Agent 在真实的新建、修订任务中能做出上述选择，结果有可检查的证据，而不只是能复述字段定义。

## 当前迭代范围

覆盖上述五个问题，包括流程记忆的新建和修订，以及写作结果的检查。调查实际 Agent 入口、已有 Memory/Skill、撰写与评审流程，并在确认后的方案中决定必要变更。

前面讨论产生的未提交字段职责规范、引用、skill 和测试改动，是本迭代的待评估方案素材，不是已确认设计或已验收结果；可以在本迭代中调整或替换。之前测试通过只能说明当时的结构和回归情况，不能替代本迭代的行为验收。

## 交付物

1. 能支撑上述理想态的实际变更，以及对应用户或 Agent 可见内容的一致性更新。
2. 一次真实复杂流程撰写和一次真实问题流程 review 的验收材料：子 Agent 任务输入、实际输出、预先记录的问题考点与逐项判定记录。
3. 实施与验证方案、开发计划、实现与验证报告、提需方验收和交付记录。

不预先要求新增某份 Statement、采用某种 Prompt、增加固定步骤或改变 CLI/DSL；这些属于方案选择。

## 验收标准

### A. 一次真实复杂流程撰写验收

由 Runner 发起一个子 Agent，向其提供真实业务要求，让其实际撰写可使用的 Procedure Memory，再检查输出是否符合预期。不能用 Runner 自己撰写的内容、Agent 复述规范或简单线性示例代替。

业务任务必须有足够复杂度，能够同时检验四字段职责、语义去重及约束作用域：包含多个有不同产物要求的步骤、实质性的条件分支和循环、全局与局部要求，以及机器结构之外的语义规范和非强制建议；必要时包含 Human 决策、字段约束或子流程。不能只因为流程过于简单，没有暴露这些选择而判定通过。具体任务与预期在实施与验证方案中预先固定。

通过条件：实际输出的 action、artifact、asserts、suggests 职责正确，没有动作混写或要求错位；已声明的格式和结构不被重复要求，混合条目中的独有语义得到保留；局部要求不被随意升级为全局，全局必要约束不会被误删，多步骤共用规则不因共用而被误判为全局；流程结构和引用合法，且没有为了避免写作问题而遗漏业务要求或简化必要控制流。按业务要求和上述问题逐项记录证据。

### B. 一次真实问题流程 review 验收

Runner 先编写一份有问题的 Procedure Memory，并在发起 review 前记录所有预埋问题的考点、位置、错误原因和预期识别结果。问题样本应覆盖 action 混写、字段职责错位、跨字段及 Schema 的语义重复、格式契约重复、局部规则错误全局化，并保留正确的语义约束和真实全局规则用于判断。

随后发起另一个子 Agent，让其独立对样本进行真实 review。不向该 Agent 提供预埋问题清单或预期答案，也不由 Runner 提前指出问题位置。样本应在现有 DSL 中可解析，使 review 实际检查写作语义，而不是仅靠语法错误发现问题。

通过条件：子 Agent 找出预先记录的所有问题；每条意见能对应到具体内容或位置，说明错误与合理修正方向。笼统评价“有重复”或“全局规则太多”不能算找到全部问题；不得把样本中的正确语义约束或真实全局规则误报为应删除的问题。Runner 将实际 review 与预先记录的考点逐项核对，记录命中、漏检和误报。

### 综合验收与证据

A、B 两项都通过，才认可本迭代修改真实有效。任一项失败时，记录原始结果并修正；需要重测时保留全部尝试及变更记录，不事后修改预期或只挑选通过的输出。

验收记录保留子 Agent 的任务输入、实际输出、Agent 配置及使用的规范版本、预埋问题考点、逐项核对结果和最终结论。证据与考点在执行前确定，不以规范文件存在、语法校验成功或历史测试通过代替两项行为验收。结论针对本次验收任务与 Agent 配置，不宣称所有模型永远不会犯错。

对最终变更仍需执行适用的仓库校验和回归；Memory 差异必须有匹配最终内容的 ChangeSet ID、校验状态和 View 入口。源文件、安装副本、安装清单及 Agent 入口保持一致。

## 后续范围与不做事项

本迭代不开展仓库全部历史记忆的批量清理，不重写已冻结 Run 的历史内容，不建立覆盖所有模型的通用可靠性保证，不新增与撰写质量无关的产品功能。是否批量治理历史 Memory 或扩大 Agent/任务评测矩阵，留待后续需求。

## 向前兼容

结论：不需要向前兼容。当前仓库 git tag --list '*stable*' 无结果，没有适用的稳定 Tag checkpoint，因此不新增历史版本兼容责任。既有有效 Memory 的解释与执行、既有 CLI/DSL 行为仍作为本迭代回归基线；如方案需要改变它们，必须明确影响并重新确认需求范围，不自动引入新语法。
