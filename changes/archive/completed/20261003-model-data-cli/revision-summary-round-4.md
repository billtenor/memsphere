## 模型 ID 统一

Human 指示：

> 这里也统一改一下吧，两套标准很奇怪。统一范式是 json-schema 的 id，统一使用 .json 作为后缀的模型 id

- 项目、市场、系统模型统一使用带 `.json` 后缀的相对路径 ID；系统模型不再保留无后缀例外或别名。例如 `memsphere/model-registration.json`、`memsphere/run/artifact.json`。
- 描述模型格式的元模型同样统一为 `json-schema/draft-07.json`、`raw.json`；登记、模型定义身份、Store 的模型绑定、Runtime 绑定、CLI 和 View 一起调整。
- 系统模型直接用完整 ID 定位文件，取消额外补后缀和展示时去后缀；移除把新的正式登记模型 ID 当作旧预览删除或转成无后缀 ID 的旧规则。
- 已有项目通过显式 `project models initialize` 完成本次转换，保留登记属性、数据及冻结的 Run/Review 产物，检查冲突并保证失败不留下部分修改。读取命令不转换；系统模型仍只读。
- 项目仍有旧系统模型 ID 时，模型命令提示先执行 initialize，不正常返回旧 ID，也不只在输出中显示尚未转换的新 ID。
- Store/Factory/Extension/Serializer ID、普通记录 ID 和目录名称不受模型 ID 规则影响，MIME 和编解码协议不变。现有按模型 ID 拼接的系统目录和 Run Store ID 须分开处理。JSON Schema 的 `$id`、`$schema` 不强行改为相对路径；不改写已有定义中的跨模型 `$ref`。
- 同步修改实施范围、后续范围、交付物、兼容性及 A17/A22，删除“系统模型 ID 保持原样”的旧要求。

## 暂不支持跨模型引用

Human 指示：

> 为了避免滥用，我们暂时不支持跨模型的引用。后续如果需要开发相关功能，我们再来做设计。这样整体设计上也简洁很多。

- 仅保留同一模型内部的定义复用，`$ref` 只接受空字符串、`#` 和 `#/...`，不支持指向其他模型、文件或网址。CLI、View 中的新建、替换定义、市场导入、业务 Store 创建及模型解码和校验入口执行同一规则，definition/runtime 两档都不能绕过；浏览、登记信息修改、删除和 initialize 仍按各自规则执行。
- `model read --part` 简化为 `all|registration|definition`，默认 definition，all 聚合两种内容；删除 references。哪些数据存储使用模型，统一由 `data store list --model` 查询。
- 更新和删除仅检查直接使用该模型的数据存储，不扫描其他模型、不做反向或传递依赖检查，不设计引用关系图。
- 旧跨模型定义保留可查看，校验和使用时报不支持；不自动展开、修复或改写。初始化只转换模型身份及归属绑定，不再承担跨模型 `$ref` 迁移。
- 新版市场第 06 个示例将状态定义放回本模型，保留内部复用和递归演示；已导入的旧版本不自动覆盖。
- 系统模型只读、统一 `.json` 后缀、完整创建检查及数据记录版本条件写等先前决策保留。跨模型引用作为后续独立需求，不预留开关或绕过方式。

## 业务 Store 配置说明

- 两种 Factory 的 `directory` 均必填，明确类型、空值、相对 Project 根解析及绝对路径规则；配置文件路径仍按 cwd。
- value 配置仅接受 directory；data 另接受已有能力 contentTypeExtensions。明确 MIME/后缀格式、默认映射、覆盖与禁用、未知字段、重复和冲突的拒绝规则。
- 补充两条可复制的最小创建示例。A6 验收示例、读回能力、移除和重登记；A23 验收配置错误、映射及不同 cwd 的目录解析。
