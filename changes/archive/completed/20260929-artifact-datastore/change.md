### 已完成的实施基线

以下能力已在 `820530e` 中实现，供 Run 接入直接使用：

- StoreId 由业务指定，在 Project 内唯一；Store 保留 `id` 和唯一绑定的 `model`。Factory 接收 StoreId，StoreBinding 包含 id，StoreRegistry 和 DataManager 按 StoreId 管理实例；同一模型可对应多个 Store。
- PayloadContent 只保证一次消费，不保证重复调用 `stream()` 重放内容；内容可持续产生，以正常 EOF 表示结束。再次读取已保存的数据时重新 `get()`。
- DataStore 的 `create/update` 接收完整 Data，消费输入流，返回 `Promise<void>`；正常 EOF 且保存完成后成功，流错误、取消或存储失败时拒绝。`get()` 返回 StoredData。
- `AppendableDataStore.append(context, data): Promise<void>` 是可选追加能力。目标须已存在，模型和 contentType 须一致；只追加输入字节。失败或取消可能留下已写前缀，不保证回滚或安全重试。
- filesystem DataStore 的 create/update 逐块写临时文件，在 EOF 后发布完整内容；append 渐进写入已有文件，运行中已写字节可见。实现不加文件锁，不保证整条追加流在并发操作中连续或原子完成。
- ValueStore 已同步 StoreId，`create/update` 仍返回 StoredValue；本轮 Run 附属数据接入使用 DataStore。

公共契约和实现边界见 [数据层设计](../../../../docs/data-layer-design.md)及 `src/data/api`。这些基础能力的代码 review 已完成，原 Run 的需求评审与后续实施方案评审仍按流程进行。

### Run 接入的已确认设计

- 保持 `Data = id + model + payload`；Artifact 使用同一个采用 raw 标准的模型。
- 当前 Artifact Store 和归档 Artifact Store 是两个独立实例，均采用 filesystem；内部装配沿用现有位置与配置，后续可以分别替换实现。
- 每个 Project 使用当前和归档两个 Artifact Store，不为每个 Run 单独创建 Store；不要求 filesystem Store 理解 Run 的业务目录规则。共享物理目录中的其他文件不因接入而被当成 Artifact 管理。
- 扩大范围不改变“每个 Store 只绑定一个模型”的约束，也不意味着将所有 Run 文件混存为 Artifact。后续已确认 Artifact、Memory 快照文件、活动日志、活动快照四个 raw 模型，每个模型当前与归档各一个 Project 级 Store，共八个 Store；具体模型 ID 和定位方式见实施方案。
- 多副本、迁移和跨 Store 一致性由业务实现，不新增抽象层的多副本写入或跨 Store 事务协议。
- 受管理的中间 Artifact 纳入 DataStore；另存为导出的本地编辑副本，以及 Agent 自行创建的临时文件，不纳入 DataStore。本轮不将 Run 状态改造成 ValueStore。

### 中间产物与 Agent 操作

- Agent 面向统一的 Artifact 操作，不需要单独操作一种名为草稿的资源；“草稿”只是框架内部对合成中间状态的称呼。
- 逐步上报时，框架合成并持久化中间 Artifact，在 Run 状态中记录关联和阶段；文件所在目录不表达阶段。
- Agent 可以将正式或中间 Artifact 另存为到指定的本地文件并编辑。导出和本地编辑本身不修改受管理内容，也不推进 Run。
- Agent 编辑后统一上报 Artifact。上报读取提交文件的内容，按当前步骤校验，通过后进入原有接纳或评审流程；不增加“先写回草稿、再正式提交”的两次操作。
- 不再要求最终上报文件必须是框架内部存储的原始路径；本地编辑副本不作为后续读取 Artifact 的持久化依赖。
- 存储位于本地还是未来的云端，不改变上述交互方式。本轮不实现云端后端。
- Review Submission 及其上下文继续保持不可变，不能被后续中间产物更新或重新上报覆盖。

### 归档、恢复与 redo

- Artifact、Memory 快照和 Agent 活动记录根据 Run 业务层提供的清单，在各自的源、目标 DataStore 之间搬运；即使两端都是本地 filesystem，也不以目录 rename 代替这些受管理内容的跨 Store 搬运。恢复采用反向流程。
- 已确认顺序：复制全部相关受管理内容，确认目标内容完整正确，再切换归档或恢复的有效位置，最后清理源 Store 中该 Run 对应的内容；不删除整个 Store。
- 复制或校验失败时，不切换有效位置，不提前删除源内容；切换后的源清理失败允许保留副本，但必须明确提示尚未清理完成并支持 redo。
- redo 指同一次归档或恢复在失败、中断后可以重新执行并完成，不要求用户手工修补文件。已完成的工作不能导致重试破坏数据；目标已有内容不能未经核实就覆盖或当作成功，不得误删其他 Run 的数据。
- Memory 快照与 Agent 活动记录也纳入跨 Store 搬运和 redo 的范围，具体清单来源与搬运协调方式待实施方案讨论。
- Run 状态等未纳入本轮 DataStore 的文件，继续沿用文件系统归档与恢复方式；中间 Artifact、Memory 快照和 Agent 活动记录不再归入这类其他文件。协调时，不得让原有目录移动再次搬运、覆盖或误删由 DataStore 管理的内容。
- 不新增归档日志、进度文件或其他中间状态存储，包括不为记录搬运进度向现有 Run 记录追加检查点。redo 依据业务记录和两端实际内容判断。此约束不禁止用于表达中间 Artifact 阶段或受管理内容清单的 Run 业务状态；清单不得用于记录搬运进度。
- redo 的具体进度识别、冲突处理、校验方法、状态切换及其他文件移动的协调方式仍须以实际代码验证；若不增加中间状态就无法安全判断，不猜测成功或删除数据，先报告具体场景并与 Human 讨论。

- Memory 快照通过 DataStore 保存和读取后，原有内容、目录结构及 Run 使用快照的行为不变。
- Agent 活动 JSON 快照与 ACP JSONL 日志通过 DataStore 持久化后，运行中可查看已到达的活动记录，读取、展示及日志重建行为保持正确。覆盖首次写入、持续写入、正常结束、取消或失败及部分内容已写入的边界；不把尚未完成的写入报告为成功，不以盲目重放掩盖追加失败。

- 归档、恢复保持原有目标位置和正常操作结果；Artifact、Memory 快照和 Agent 活动记录通过各自的 Store 搬运，Run 状态等未纳入数据层的文件沿用原有文件系统方式。不丢失受管理内容，不误删其他 Run 的内容，不将不完整操作报告为成功。
