# Issue #137：共享Project数据、App配置与开发者自定义设置界面

## 本轮调整依据

原需求是App不能通过公开上下文连接Project中已有业务Store，导致App与CLI无法共享同一份权威数据。原第七版需求全文与Human历史确认已通过原生入口导出并作为固定External提供，供核对原范围；其确认是历史事实，回溯后不再作为本版有效批准。已有实现代码保留在PR https://github.com/billtenor/memsphere/pull/141 ，当前工作基线d3d993b34b3f18c3b697cb048103bd544621412e；历史技术验收不作为本版GUI符合性证据。本版完整要求重新提交产品Agent与Human确认，尚未合并或取得当前交付票。

本轮Human查看View后指出“不是要给 app 做一个持久化的配置吗？配置在哪里呢？”，进一步明确要求：

> view 的设置栏，专门设置一个给app 创建设置的地方吧
>
> 一级菜单是 app，进去之后就是各种外部安装的 app，一个 app 一个配置页面

这是本轮范围调整的直接依据：不能只交付CLI和JSON配置文件，必须在现有View设置栏提供App入口及每App独立配置页面。本版对照固定历史原文保留共享数据、来源保护与兼容性要求（下文“已有共享数据动线”与验收逐项列明），同时新增以下可见配置体验；原“通用配置GUI不在本轮”的范围排除在此被明确替换。Human新指令是该方向的执行授权，不冒充对本完整修订PRD的正式通过票。产品Agent与Human继续同时参与正式评审。

原始需求来源：[Issue #137](https://github.com/billtenor/memsphere/issues/137)，要求App backend通过公开上下文显式绑定已登记的Project Store，提供模型/类型校验及公开访问接口；本版选择显式绑定方案，不采用数据迁移。上述View设置页是本轮Human新增指令，非原Issue已经要求的细节。

## 要解决的问题

用户在View里找不到App配置入口，不知道当前App用了哪个Store，也不能直接调整配置；仅提供CLI命令不足以完成其希望的产品动线。

交付后，用户进入设置栏，看到一级菜单“App 配置”，打开后看到当前Project中外部安装的App；选择某一个App，就进入专属于它的配置页面。不同App的设置分别展示、分别保存，不混在Project或全局配置的大表单里。App开发者声明配置需求，并可为自己的App提供专属设置界面；未提供时仍可使用宿主的通用配置能力。安装者从统一入口进入对应App页面填写实际值；通用界面、自定义界面与CLI修改的是同一份持久化安装配置。

## 最新产品反馈与本版变化

Human在真实View中检查交互原型后表示“看原型没问题了”，并要求入口名称为“App 配置”。该反馈确认当前原型的界面方向；原型使用明确标注的示例App和浏览器本地数据，不证明真实App配置持久化或扩展能力已经交付，也不替代对本版完整需求的正式通过票。

Human同时要求：“你还得考虑给 app 的开发者开放什么样的扩展点，让他们去做自己 app 的设置界面。这个需求文档里把需求描述一下，具体技术方案可以后面再弄”。因此本版新增开发者可为自己的App提供专属设置界面的产品能力要求；具体接口、声明格式、加载/渲染方式和生命周期留给后续技术方案，本需求不预先指定。

## 采用的项目规范与检查范围

- `procedures/memsphere-agile-requirement-development`：继续同一Run，先确认本版范围、修订方案，再实现与正式技术/产品验收；产品Agent和Human同时参与。本版不新增流程或Memory DSL语义。
- `statements/memsphere-repository-development-rules`：本Run冻结规范。新增用户可见设置入口需同步对应System Memory的reserved-memory源与当前开发Project副本，检查Skill冗余说明并更新文档。Memory发生差异时执行Store validate与最终ChangeSet校验，保留匹配版本证据。未修改Memory实体、Schema或Run/Review运行时的规则不自动触发其专用套件；若后续实现实际触及，再按改动映射追加。
- `statements/memsphere-repository-testing-rules`：本Run冻结规范。按真实边界分层，先运行受影响测试，补HTTP保存/失败/冲突/权限与真实浏览器交互验证；前端调整须使用playwright-cli实际操作，异步等待真实状态并有期限，不以固定sleep判断成功。适用测试之外不为凑覆盖扩大范围；发现新风险或失败再追加必要验证。
- `concepts/memsphere-app`、`statements/memsphere-app-usage-rules`：App发行声明、Project安装配置、可信本地代码与公开访问入口的语义参考；当前内容作为辅助，本轮新增界面会同步更新，不作为冻结正式规则的替代。
- `concepts/memsphere-view`及仓库View SDK/Reference Module：设置页沿用现有Settings Module、Shell和公共UI服务，避免宿主私有DOM/CSS耦合；实际检查桌面/窄屏、键盘、加载/错误状态和卸载清理。不涉及通用View插件协议新增。

Human明确指令“full 检查不用管，你继续流程”继续有效，原文External作为依赖固定。本轮不运行或等待full，不声称full通过；default CI与覆盖新增页面、持久化、权限、冲突和旧行为的受影响验证照常执行。该指令只限定full检查，不豁免适用验证、文档/Memory同步、产品Human票或合并授权。

## 谁负责什么

- Project使用者或Agent准备模型，登记并管理业务Store及数据。
- App开发者声明配置及Store需求，并可通过受支持的扩展能力提供自己App的设置界面，组织字段、布局及交互；不需要为了新增一个App的设置去修改Memsphere核心。用户不需要编辑App发行清单或宿主内部路径。
- 安装者选择当前Project中实际目标Store，在该App自己的设置页修改、校验并保存配置。
- Memsphere按App声明和当前Project登记验证并保存，展示真实生效目标；拒绝不兼容/失效目标，不偷偷复制数据或创建备用空Store。

模型描述结构，Store承载数据，App用途key是App内部名字，Project Store ID是实际数据源。配置是当前Project中该App的设置，同一App安装到不同Project可有不同配置；重启View、刷新页面或再次打开后保持已保存值。

## 设置栏导航和具体页面

1. **进入App。** 在现有View设置栏新增一级菜单“App 配置”。入口在没有安装App时也可见；没有Project时清楚提示选择Project。
2. **查看外部安装的App。** 打开App入口显示当前Project已安装App的名称、ID、版本和启用状态；列表来自实际安装登记，不把内部View Module、主题或系统配置混为App。没有App时显示“当前项目尚未安装App”及现有安装方式说明，不虚构示例数据。本轮不在此增加安装、升级或卸载流程。
3. **选择某个App。** 每个App有自己的可直接访问、可刷新的配置页面，可返回App列表。标题明确App名称与当前Project，未安装/已消失的App清楚报错，不切到别的App。
4. **编辑这个App的配置。** 展示已保存值，按其声明展示可编辑配置项及必填/格式说明。常用字段应能在页面填写，不要求用户为Store绑定手写JSON文件。复杂配置可提供清楚标注的结构化内容编辑方式，必须保留原结构和值，不能因页面只展示部分字段而丢弃其他配置。App无可编辑配置时显示说明，不显示一个无法保存的空表单。
5. **选择Store。** 对App声明的Project Store需求，显示用途key、所需模型、类型和实际Store ID；从当前Project中已登记且模型/类型匹配的Store选择。缺失或不兼容的旧目标仍须清楚显示原因，不能被默认候选静默替换。无匹配项时显示原因及准备Store的方法，不自动新建。保存仍需以实际最新登记为准校验。
6. **校验和保存。** 页面明确区分未保存编辑和已保存配置。用户主动保存时校验配置格式、App约束及Store绑定，成功给出可见反馈并重新显示实际保存值；失败保留编辑并定位原因，原有效配置和数据不被修改。成功保存只影响当前Project的该App，不影响其他App/Project。
7. **应用与持久化。** 重新加载配置页和重启View后都看到同一保存结果；CLI app configure与页面互通，app show与页面展示的实际绑定一致。页面明确分开“已保存配置”和“运行状态”：保存成功只证明配置已持久化；某些backend/View配置需要重启时，显示“已保存，待重启”，不能笼统标为“已应用”。已运行界面或backend实例的实际状态能可靠确认时才展示，不可确认时说明尚未确认，不根据磁盘值推断当前界面已经切换。
   - Store绑定的原契约保持：配置从A有效保存为B后，宿主新发起的共享Store backend调用采用B，旧来源提交被拒绝，改绑前已开始的独立调用可完成于A。
   - 需要重启的页面/模块或其他配置快照可能仍显示旧界面；此时配置页显示已保存B与待重启提示，不承诺所有运行实例已更新，也不把旧界面显示A当作允许旧来源写入的依据。重启后须通过实际新调用和重新打开页面确认B。
   - 例如：A→B保存后立即看到“已保存：B”；如有重启要求，同时看到“待重启”。不可确认的运行目标标为未确认。重新加载配置页仍是已保存B；旧A页面提交被拒绝；重启后重新读取的记录来自B，展示与实际调用一致。
8. **离开与并发。** 编辑后切换App、Project或离开设置时避免静默丢弃，提供可理解的放弃/继续编辑选择。若其他窗口或CLI已修改该App配置，保存旧页面不能无提示覆盖新配置，应提示重新加载并保留用户可恢复的编辑。

权限沿用现有设置机制；未经授权不能读取或修改受保护设置。Mounted来源保持只读，不借此增加写权限。错误、加载、空列表、保存中和取消状态都能清楚辨认。页面在桌面、窄屏和键盘操作下可用，并沿用现有设置视觉与导航惯例。

## App开发者的设置界面扩展需求

### 为什么需要

不同App的设置不一定适合相同的通用表单。例如费用App希望把费用Store、默认币种和展示偏好组合在自己的页面中，任务App希望按自己的业务语言组织默认视图和任务展示设置。仅能声明几个字段、由宿主统一生成表单，不能覆盖开发者对设置布局和交互的需要。

### 开发者应能做什么

1. **提供自己的设置界面。** App开发者可以为该App提供专属设置界面，自主组织配置项、说明、布局和交互；它作为该App的一部分交付或登记，经受支持的扩展方式被宿主识别。开发者不需要改Memsphere核心，不需要让用户另找地址或手动登记一个独立的设置入口。
2. **接入统一入口。** 用户仍通过“设置 → App 配置 → 对应App”进入；App列表、当前Project、App身份和返回入口由宿主保持一致。自定义设置界面出现在这个App的独立配置页面中，不成为另一个并列的全局设置系统，不混淆不同App或Project。
3. **取得当前配置并提交修改。** 自定义界面应能在明确的当前Project/当前App上下文中读取已保存配置、编辑候选值、请求校验及保存，并得到可展示的校验、冲突、成功和需重启状态。这里列的是开发者需要获得的能力，不规定具体API、函数名或通信协议。
4. **支持App自己的配置体验。** 开发者可根据本App业务展示字段说明、动态选择和相互关联的设置，提供有意义的输入提示与配置校验；需要Project Store时，仍能让用户看清用途、模型、类型和实际目标。具体业务校验如何声明或接入由技术方案确定，不能以“自定义页面”为理由跳过宿主的最终校验。
5. **沿用同一份持久化配置。** 自定义页、宿主通用页和CLI的保存/读取结果互通。自定义页不能把只写入浏览器缓存的结果显示为真实配置已保存，也不能另建一份无法与App运行和CLI一致的权威配置。保存失败不改变原有效配置；涉及Store改绑时继续遵守来源保护。

### 宿主与App的责任边界

- 宿主负责统一入口与身份边界、权威配置的保存、适用权限与最终合法性检查、并发更新保护和保存/运行状态的真实结果。开发者可以定制页面，但不能据此获得修改其他App或其他Project配置的新权限。
- App负责专属配置内容与交互，按受支持的配置能力读取、提交并呈现错误和应用状态；应能把未保存编辑状态与宿主协作，用户切换App、Project或离开时不能静默丢弃修改。具体协作方式后续设计。
- 自定义页和通用页都必须保留未编辑字段及原有配置结构，不能因页面只覆盖部分配置而静默删除其他值。前端提示不能替代宿主对最新配置、模型/类型、Store登记及来源身份的校验。
- 本轮沿用“可信本地App”的运行边界，不借设置扩展引入不可信代码沙箱的承诺，也不把页面扩展当成可绕过权限、校验或协调协议的通道。
- 自定义界面应融入现有View的主题与基本可用性规范；宿主保持可辨识的App/Project和返回路径。具体容器、样式服务和扩展生命周期由技术方案确定。

### 没有或加载失败时

没有提供自定义界面的App，继续使用宿主通用配置能力，原有App和CLI配置兼容，不强制所有App作者重写设置页。既无自定义界面也无可编辑配置的App，显示无可配置项说明。

已声明自定义界面但加载失败时，应在该App页明确显示失败及可理解的恢复方式，不显示保存成功，不改变已保存配置，也不拖垮其他App或整个设置导航。存在可用通用配置入口时可以提供清楚标注的返回/查看方式，不能静默替换页面并掩盖失败。详细降级和恢复机制留给技术方案。

### 用户可以怎样判断完成

安装一个提供自定义设置界面的示例App，以及一个只使用通用配置的App。从同一“App 配置”列表进入时，前者展示开发者定义的专属布局和交互，后者正常展示通用配置；两者都有明确的当前App/Project与返回入口。分别编辑、校验、保存后，刷新或重启以及CLI读取都能确认同一保存值，且不同App之间不串值。自定义页的校验失败、并发冲突、未保存离开和加载失败场景均不误报成功、不破坏原配置。

## 已有共享数据动线仍需成立

1. App作者声明需要何种模型和ValueStore或DataStore，backend通过公开上下文访问。
2. 用户在Project登记含既有记录的Store，将App需求绑定到它；App读取既有数据，App写入后CLI可读，CLI更新后App可读。两类Store均支持，不复制、不清空、不迁移数据。
3. CLI安装/配置入口继续兼容；无绑定、未声明key、目标缺失、模型或类型不符均明确失败，不回退。已有自有Store App无需迁移。
4. A改绑B前校验B。无效B不能替换旧有效配置；有效B后新调用用B，改绑前已开始的调用可完成于A；查看结果显示实际目标。
5. 从A读取后改绑B，遵循来源传递约定的旧保存/删除被拒绝，该次旧请求不修改A/B。示例调用端清楚提示来源变化，刷新并显示B及当前记录，不自动重试；用户重新发起并确认后才操作B。宿主提供并验证token，App保存来源并展示提示，不能宣称任意第三方App自动具备页面提示。
6. App按契约处理预期错误并成功完成时允许成功；未处理失败明确报错，遵循Human“允许就不报错，不允许报错才报错”的澄清。目标被移除或不兼容后明确失败，重新配置有效目标后恢复。

## 验收标准

- 设置栏有一级“App 配置”菜单；列表对应实际外部安装App，空态和无Project明确。
- 安装两个不同配置的App后，各有独立配置页，直接链接/刷新正确，切换不串值。没有配置的App得到准确说明。
- 在一个App页面修改普通设置和Store绑定，保存后刷新、重启View、CLI查看均一致；其他App/Project未改变。CLI改配置后页面重新加载能看到同一结果。A→B保存后，页面明确显示已保存B以及需要时的待重启状态；运行目标仅在可靠确认时展示，否则标注未确认；不把保存等同所有运行界面已应用。重启前验证新共享Store backend调用用B和旧来源拒绝，重启后实际新调用与界面共同确认B。
- Store候选按模型/类型筛选；旧绑定无效时不被静默替换，提交不合法配置/失效Store明确失败，原有效配置及A/B数据保留。
- 有未保存编辑时离开/切换有保护；两个窗口/CLI并发修改时旧版本不静默覆盖新配置。取消和失败可保留或恢复编辑。
- 无token或不允许的来源不能修改，Mounted目标不变为可写；错误消息可诊断，失败不伪装成保存成功。
- 共享ValueStore/DataStore、旧来源保存/删除保护及原App自有Store兼容标准继续通过，配置页新增入口不改变这些语义。
- 自动化验证覆盖真正HTTP及保存持久化/失败路径；实际浏览器验证App导航、两App分开编辑、Store选择、校验、保存/刷新、冲突/离开保护、空态、窄屏及键盘，等待真实状态而非固定sleep。
- 至少一个由App开发者提供的专属设置界面通过统一入口展示，不需要修改宿主核心来硬编码该App页面；另一个未提供自定义页的App继续使用通用配置。两者身份清楚、配置持久化与CLI互通，不相互影响。
- 自定义设置页覆盖校验反馈、保存失败、并发冲突、未保存离开保护及加载失败；不得误报成功或破坏旧配置/其他App页面。只编辑部分配置时，未编辑字段保留。
- 文档、对应System Memory和Skill说明同步实际界面、开发者可用的设置扩展能力及CLI配置互通规则，提供有效Memory Store与ChangeSet校验证据；不声称本轮尚未实现的页面已经存在。

## 范围和后续

本轮新增“App 配置”入口、已安装App列表、每App独立配置页、开发者提供自定义设置界面的扩展能力、无自定义页时的通用配置兼容，以及同一份配置的持久化保存、校验和可见反馈，保留既有CLI和共享数据能力。准确路由、扩展声明与分发格式、API、渲染/加载方式、生命周期、配置表单实现和并发版本字段均由后续修订技术方案确定；本需求不指定这些技术选择，不授权新增Memory syntax关键字。
